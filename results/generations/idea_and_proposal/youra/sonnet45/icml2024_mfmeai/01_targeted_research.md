   from robotic_transformer_pytorch import MaxViT, RT1

   from transformers import AutoModel, AutoProcessor
   processor = AutoProcessor.from_pretrained("IPEC-COMMUNITY/spatialvla-4b-224-pt")

**API Usage Patterns:**
- **LoRA Fine-tuning**: Most VLA implementations support parameter-efficient fine-tuning via LoRA

- **Guidance Scale**: Classifier-free guidance (cfg_scale 1.5-7) commonly used
- **Precision**: BF16/FP16 inference standard for efficiency

- **PyTorch**: Dominant (95%+ of implementations)

### Identified Gaps

#### Gap 1: Bridging High-Level Reasoning and Low-Level Control in Real-Time

**Current State:**
- Most VLA models operate end-to-end (e.g., OpenVLA, RT-2) OR use dual-brain architectures (e.g., UnderwaterVLA, Maestro)
- End-to-end models: Struggle with real-time low-level control precision (<10Hz for 7B models per SmolVLA)
- Dual-brain models: Achieve better responsiveness but sacrifice unified reasoning
- Existing solutions: Either sacrifice speed (large unified models) or reasoning coherence (decoupled systems)

**Missing Piece:**
- Unified architecture that maintains coherent multi-step reasoning while achieving <5ms action inference for real-time control
- Adaptive computation allocation: Dedicate more compute to high-level planning for novel situations, less for routine low-level control
- Hierarchical temporal abstraction that allows planning at multiple time scales (100ms for reactive, 1s for tactical, 10s for strategic)

**Potential Impact:**
- CRITICAL for safety-critical applications (autonomous vehicles, surgical robots, industrial manipulation)
- Could enable MFMs to handle 10-100x more complex tasks by freeing high-level reasoning from low-level control bottlenecks
- Reduce deployment costs by enabling real-time performance on edge devices (currently most VLAs require cloud GPUs)

- HIGH for contact-rich manipulation (assembly, deformable object manipulation, medical procedures)
