# Research Idea: Git-Mem

## Title
Git-Mem: Lightweight Cryptographic Provenance for Auditable LLM Agent Memory Systems

## Motivation
LLM agents with external memory systems face critical security vulnerabilities—the AgentPoison attack achieves 80%+ success rates by injecting poisoned memories without detection. Current systems like A-MEM lack auditability mechanisms, creating risks for deployment in regulated domains (healthcare, finance) requiring GDPR/HIPAA compliance. Existing blockchain-based solutions impose prohibitive overhead (>100ms), making them unsuitable for real-time agent reasoning. This research addresses the urgent need for trustworthy, auditable agent memory that maintains real-time performance.

## Main Idea
We propose Git-Mem, applying Git's proven cryptographic provenance architecture (Merkle trees + hash chains + ECDSA signatures) to LLM agent memory systems. Each memory operation creates a signed transaction with content hashes, organized in Merkle trees for O(log n) verification. Temporal hash chains ensure immutability—any tampering breaks cryptographic commitments, enabling real-time attack detection.

**Hypothesis:** Git-Mem reduces memory poisoning attack success from 80%+ to <5% while maintaining <10ms overhead through adaptive batching of Merkle updates.

**Methodology:** Controlled experiments comparing Git-Mem against A-MEM baseline using AgentPoison attacks across HAICOSYSTEM's 92 safety scenarios, measuring latency (Welch's t-test, n=1000 operations) and attack resistance (two-proportion z-test, n=100 attacks).

**Impact:** First auditable agent memory system enabling regulatory compliance, with open-source implementation as drop-in replacement for vulnerable systems.

## 3. Causal Mechanism

### Mechanism Chain

```
Cryptographic Hash Function (SHA-256)
    ↓ (collision resistance)
Memory Operation → Signed Transaction
    ↓ (ECDSA signature)
Merkle Tree Organization
    ↓ (root hash commitment)
Temporal Hash Chain
    ↓ (immutability)
Tamper-Evident Audit Trail
    ↓ (verification protocol)
Attack Detection + Auditability
```

### Detailed Mechanism

**Step 1: Transaction Creation**
- Each memory operation (store, retrieve, update, delete) creates a signed transaction
- Transaction = {timestamp, operation_type, agent_id, content_hash, parent_hashes, ECDSA_signature}
- Content hash prevents tampering (SHA-256 collision resistance: ~2^128 operations)

**Step 2: Merkle Tree Commitment**
- Memory entries organized as Merkle tree leaves
- Internal nodes = Hash(left_child || right_child)
- Root hash = cryptographic commitment to entire memory state
- O(log n) verification: only log2(n) sibling hashes needed to prove inclusion

**Step 3: Temporal Chain Linking**
- Root hashes linked chronologically (similar to Git commit DAG)
- Each root hash includes parent_root_hash creating immutable history
- Any alteration breaks chain, detectable via hash mismatch

**Step 4: Attack Detection**
- Poisoned memory insertion changes content_hash
- Merkle root hash recomputation fails verification
- ECDSA signature mismatch reveals unauthorized modifications
- Detection latency: Real-time (during memory operation)

1. **Cryptographic Primitives → Tamper Evidence**

## 8. Statistical Verification Design

### Study Design

**Type:** Controlled comparative experiment with between-subjects design
- **Factor A:** Memory System {A-MEM, Git-Mem}
- **Factor B:** Attack Presence {No Attack, AgentPoison Attack}
- Design: 2×2 factorial with 4 conditions

### Sample Size Calculation

**Performance Evaluation:**
- Effect size: δ = 10ms (meaningful overhead threshold)
- Baseline variance: σ = 5ms (typical memory operation variance)
- Cohen's d = δ/σ = 2.0 (large effect)
- Power: 1-β = 0.90, α = 0.05
- **Required sample size:** n = 22 per condition (total: 88 trials)
- **Planned sample:** 1000 operations per condition (conservative)

**Attack Resistance Evaluation:**
- Baseline success rate: p0 = 0.80 (AgentPoison)
- Target success rate: p1 = 0.05 (Git-Mem)
- Effect size: h = 2.03 (very large)
- **Required sample size:** n = 12 attacks per condition
- **Planned sample:** 100 poisoned memories injected (conservative)

### Statistical Tests

**H1 (Performance):**
- Test: Welch's t-test (overhead: Git-Mem vs. A-MEM)
- Null hypothesis: μ_GitMem - μ_AMEM ≥ 10ms
- Alternative: μ_GitMem - μ_AMEM < 10ms (one-tailed)
- Significance level: α = 0.05
- Bonferroni correction: α/3 = 0.0167 (3 predictions)

**H2 (Security):**
- Test: Two-proportion z-test (attack success rates)
- Null hypothesis: p_GitMem = p_AMEM = 0.80
- Alternative: p_GitMem < 0.10 (one-tailed)
- Significance level: α = 0.0167

**H3 (Scalability):**
- Test: Logarithmic regression (verification time vs. N)
- Model: T = a × log(N) + b
- Null hypothesis: Coefficient significantly different from log(N)
- Alternative: Coefficient ≈ c × log(N) within 50% tolerance
- Goodness-of-fit: R² > 0.95

### Confounding Controls

1. **Hardware:** All experiments on identical hardware (AWS c5.2xlarge: 8 vCPU, 16GB RAM)
2. **Software:** Fixed Python 3.10, cryptography.io v42.0, SQLite 3.40
3. **Workload:** HAICOSYSTEM scenarios executed in randomized order
4. **Agent Model:** Fixed LLM (GPT-4 via API, temperature=0 for reproducibility)
5. **Memory Size:** Control for number of memory entries (vary: 1K, 10K, 100K, 1M)

### Reproducibility Protocol

- Random seed: Fixed for A-MEM organization
- Attack injection: Deterministic selection (every 10th memory slot)
- Timing: Median of 5 runs per condition
- Code availability: Open-source implementation with Docker container
- Data availability: Anonymized latency measurements and attack logs
