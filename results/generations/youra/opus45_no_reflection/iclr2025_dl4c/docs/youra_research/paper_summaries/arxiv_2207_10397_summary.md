# CodeT: Code Generation with Generated Tests

## Key Metadata
- **Authors:** Bei Chen et al.
- **Year:** 2022
- **Venue:** arXiv (preprint 2207.10397)
- **Core Contribution:** Proposes **CODET**, a **test-generation + execution-consensus** method that uses the *same* LLM to generate tests and then selects the best code sample via a **dual execution agreement** score.

## Section Summaries

### Abstract
The task of generating code solutions for a given programming problem can bene-
ﬁt from the use of pre-trained language models such as Codex, which can produce
multiple diverse samples. However, a major challenge for this task is to select
the most appropriate solution from the multiple samples generated by the pre-
trained language models. A natural way to evaluate the quality and correctness
of a code solution is to run it against a set of test cases, but the manual creation
of such test cases is often costly and time-consuming. In this paper, we propose
a novel method, CODET, that leverages the same pre-trained language models to
automatically generate test cases for the code samples, thus reducing the human
effort and increasing the coverage of the test scenarios. CODET then executes the
code samples using the generated test cases and performs a dual execution agree-
ment, which considers both the consistency of the outputs against the generated
test cases and the agreement of the outputs with other code samples. We con-
duct comprehensive experiments on four benchmarks, HumanEval, MBPP, APPS,
and CodeContests, using ﬁve different pre-trained language models with varying
sizes and capabilities. Our results show that CODET can signiﬁcantly improve the
performance of code solution selection over previous methods, achieving remark-
able and consistent gains across different models and benchmarks. For instance,
CODET improves the pass@1 metric on HumanEval to 65.8%, which represents
an absolute improvement of 18.8% over the code-davinci-002 model, and an ab-
solute improvement of more than 20% over the previous state-of-the-art results.

### Introduction & Motivation
Large code LMs (e.g., Codex) can generate many candidate programs per prompt, yielding high **pass@100** but much lower **pass@1**, making deployment difficult because users typically want *one* correct answer. Execution-guided selection is an obvious remedy, but it presumes access to high-quality tests—expensive to write and unrealistic in tools like Copilot. The paper addresses the gap by **automatically generating tests** from the same LLM and using them to rank/select candidates without training a separate verifier or needing labeled data. The key idea is that correct solutions should both (i) pass many generated tests and (ii) agree in behavior with other independently sampled solutions.

### Methodology
CODET (“**CODE generation with generated Test-driven dual execution agreement**”) takes a programming problem context \(c\) (NL description + function header/imports) and samples \(n\) candidate solutions from a pretrained code LM \(M\):
\[
X=\{x_1,\dots,x_N\}=M(c).
\]
**Test generation** uses the *same* model \(M\), but appends an instruction prompt \(p\) designed to elicit `assert`-style I/O checks rather than code. The instruction includes: (1) a `pass` placeholder for the function body, (2) a comment like “check the correctness of [entry point]”, and (3) an initial `assert` to enforce an input–output assertion format. Test cases are then sampled as
\[
Y=\{y_1,\dots,y_M\}=M(\text{concat}(c,p)).
\]
To avoid leaking ground-truth signals, they **remove example I/O pairs** from the original benchmark prompt before generating both \(X\) and \(Y\).

**Dual execution agreement (DEA)** is inspired by RANSAC: execute each code \(x\) on each generated test \(y\); define a “hypothetical inlier” pair \((x,y)\) if \(x\) passes \(y\) (runs without error and matches expected output). For an inlier, compute:
- \(S_y\): the subset of tests in \(Y\) that \(x\) passes.
- \(S_x\): the subset of solutions in \(X\) that pass **exactly the same** test subset \(S_y\) (functional equivalence under generated tests).
Then define a **consensus set**
\[
S=\{(x,y)\mid x\in S_x,\ y\in S_y\},
\]
and score it by
\[
f(S)=|S_x|\cdot |S_y|.
\]
Selection: choose any solution \(\hat{x}\in S_x\) from the **highest-scoring** consensus set; to output top-\(k\), pick from top-\(k\) consensus sets.

Implementation note: rather than random RANSAC sampling, when \(N\) is manageable they use a **naïve exhaustive** version: for each \(x\), record its passed-test bitmask over all \(y\in Y\), then group solutions by identical bitmasks to directly obtain all \(K\) consensus sets. Reported hyperparameters include **temperature \(=0.8\)**; typical sampling uses **\(n=100\)** solutions and up to **500 generated tests/problem** on HumanEval (details below).

### Experiments & Results
**Benchmarks & splits.** Evaluation uses standard public code-generation benchmarks in **zero-shot** settings: **HumanEval** (164 problems), **MBPP** (427), **APPS** (Intro 1,000 / Interview 3,000 / Competition 1,000), and **CodeContests** (165). Table 1 reports average numbers of **ground-truth tests per problem**: HumanEval \(\approx 100\), MBPP \(\approx 3.1\), APPS \(\approx 20.99\), CodeContests \(\approx 203.7\). For each problem they sample \(n\) candidate programs: **\(n=100\)** for HumanEval/MBPP, **\(n=50\)** for APPS (compute-saving on 5,000 test problems), and **\(n=1000\)** for CodeContests (very hard). Prompts remove example I/O from problem statements; for APPS/CodeContests they wrap description as a comment and use a uniform signature `def solution(stdin: str) -> str:` to match interactive I/O.

**Models.** Five pretrained LMs: OpenAI Codex (**code-cushman-001**, **code-davinci-001**, **code-davinci-002**), **INCODER-6B (6.7B)**, and **CODEGEN-MONO-16B**.

**Metric.** They use functional correctness via **pass@k** (Chen et al., 2021) computed from ground-truth unit tests. Baseline pass@k is the **unbiased** estimator given \(n\) samples and \(c\) correct samples:
\[
\text{pass@}k = 1 - \frac{\binom{n-c}{k}}{\binom{n}{k}}.
\]
Baseline selection is random \(k\)-subset of \(n\); CODET deterministically selects \(k\) solutions via DEA consensus ranking.

**Baselines compared.**
1. **Baseline**: unbiased pass@k with random selection among \(n\).
2. **AlphaCode-C** (Li et al., 2022b): clustering solutions by outputs on generated inputs and ranking clusters by size; they replicate it using CODET-generated test inputs.

**Main results (zero-shot).** CODET consistently improves pass@1 and pass@10 across models and benchmarks.

| Benchmark | Model | Baseline pass@1 | CODET pass@1 | Abs. gain |
|---|---:|---:|---:|---:|
| HumanEval | code-cushman-001 | 33.5 | 44.5 | +11.0 |
| HumanEval | code-davinci-001 | 39.0 | 50.2 | +11.2 |
| HumanEval | code-davinci-002 | 47.0 | **65.8** | **+18.8** |
| HumanEval | INCODER-6B | 16.4 | 20.6 | +4.2 |
| HumanEval | CODEGEN-MONO-16B | 29.7 | 36.7 | +7.0 |
| MBPP | code-davinci-002 | 58.1 | 67.7 | +9.6 |
| MBPP | INCODER-6B | 21.3 | 34.4 | +13.1 |

CODET’s **pass@2** often approaches the baseline **pass@10**, indicating substantial sample-efficiency gains in selecting good candidates. AlphaCode-C is “consistently inferior to CODET” across models on HumanEval/MBPP, supporting the benefit of incorporating both **test coverage (|Sy|)** and **solution agreement (|Sx|)** via \(f(S)=|S_x||S_y|\).

**APPS & CodeContests (code-davinci-002, zero-shot).**

| Benchmark | Level | Baseline pass@1 | CODET pass@1 | Abs. gain |
|---|---|---:|---:|---:|
| APPS | Intro | 27.2 | 34.6 | +7.4 |
| APPS | Interview | 5.1 | 8.1 | +3.0 |
| APPS | Competition | 1.8 | 2.2 | +0.4 |
| CodeContests | — | 0.7 | 2.1 | +1.4 |

Gains shrink on the hardest settings (APPS-Competition, CodeContests), and the authors note code-davinci-002 may output many **trivial** solutions on these tasks; they claim robustness analyses in an appendix.

**Ablations/analyses highlighted in the main text.**
- **Test-case quantity (HumanEval, code-davinci-002):** generate up to 100 samples of tests, extract up to `Limit` tests per sample (syntactically correct). With **Sampling Number=100, Limit=5** (≤500 tests), pass@1 reaches **65.8**. Even with very few tests, CODET helps: e.g., **Sampling Number=10, Limit=1** yields **56.5** pass@1; performance saturates around Sampling Number ≥ 50 and Limit ≥ 3.
- **Test-case quality diagnostics:** test-case **accuracy** = fraction of generated tests passed by the **canonical solution**; **toxicity rate** = fraction of tests where *some generated solution* passes but the canonical solution fails (can mislead selection). Codex models generate higher-accuracy, lower-toxicity tests than INCODER/CODEGEN; Codex tests also show high reported code coverage (average >95% under two coverage criteria; details referenced to appendix).
- **Using better tests to boost weaker models:** replacing a weaker model’s generated tests with **code-davinci-002** tests improves selection. Example pass@1 gains (HumanEval/MBPP) relative to using “own” tests include: code-cushman-001 **+2.6 / +4.3**, code-davinci-001 **+1.8 / +2.4**, INCODER-6B **+6.2 / +15.9**, CODEGEN-MONO-16B **+11.0 / +10.5** (Table 4).

**Computation cost.** No explicit GPU-hours are reported in the provided content, but the paper explicitly reduces sampling on APPS to **\(n=50\)** “to save computation cost” and uses **\(n=1000\)** on CodeContests following AlphaCode-style evaluation.

### Discussion & Conclusion
CODET shows that LLMs can partially “self-verify” by generating tests and using execution-based consensus to select among samples, yielding large pass@1 improvements without training a separate ranker. Limitations include applicability only to **executable** code tasks and the **extra compute** needed to generate/execute many tests; failures also occur when prompts are ambiguous or tests miss corner cases. Future work is proposed around reducing cost and improving performance on harder problems.

## Key Contributions
- Introduces **CODET**, which **generates test cases in zero-shot** from the same pretrained code LM used for solution sampling, avoiding labeled test-generation training.
- Proposes **dual execution agreement** (RANSAC-inspired) that ranks candidate solutions by a consensus score \(f(S)=|S_x||S_y|\), combining **test coverage** and **inter-solution functional agreement**.
- Demonstrates large, consistent **pass@1** improvements across models/benchmarks (notably **HumanEval 47.0→65.8** with code-davinci-002; +18.8 absolute), outperforming prior reported SOTA in this setting.

## Potential Relevance
CODET is directly useful for hypotheses about **self-consistency/self-verification** in program synthesis: its consensus objective formalizes how *agreement among samples* plus *execution evidence* can replace learned verifiers. The paper’s analyses (test accuracy/toxicity, saturation with fewer tests, and “strong-test generator helps weak-code generator”) provide concrete experimental handles for studying when verification-by-generation works and how to allocate compute between sampling solutions vs sampling tests.
