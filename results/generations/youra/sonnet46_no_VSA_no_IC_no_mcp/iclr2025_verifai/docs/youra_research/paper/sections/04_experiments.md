# Experimental Setup

We design experiments to answer five research questions that form a causal
chain, testing each link from signal existence through LLM consumption to
overall pass@1 improvement. This pre-registered structure ensures that a
null h-m3 result (no overall improvement) can be diagnosed: is it because
mypy produces no signal (h-e1 fail), the LLM doesn't use it (h-m1 fail),
or some other reason?

**RQ1 (h-e1):** What fraction of GPT-4o-mini's failing solutions on
HumanEval+ and MBPP+ have mypy-detectable errors? Does the signal exist
at a density sufficient to drive repair improvement?

**RQ2 (h-m1):** Under Condition B (execution+mypy), does the mean number
of mypy errors per problem decrease monotonically across repair rounds 1–5?
Does the LLM consume and act on mypy feedback?

**RQ3 (h-m2):** Is the pass@1 improvement concentrated on type-error
problems (problems where mypy detected at least one error in the initial
solution)? Does the improvement follow the type-specificity mechanism?

**RQ4 (h-m3):** Does execution+mypy repair (Condition B) achieve higher
pass@1 than execution-only repair (Condition A) on HumanEval+, across
multiple seeds?

**RQ5 (h-z1):** On a curated arithmetic subset where valid Z3 specifications
can be generated, does adding Z3 counterexample feedback (Condition C)
further improve pass@1 beyond Condition B?

## Datasets

**HumanEval+** [Liu et al., 2023]: 164 Python programming problems, each with
a function signature, docstring, and substantially expanded test suite (vs.
original HumanEval). We use HumanEval+ as our primary benchmark for the
controlled comparison (RQ4/h-m3). It is the correct primary test bed because
h-e1 establishes a 70% mypy error rate in failing solutions — the signal is
dense enough to test.

**MBPP+** [Liu et al., 2023]: 378 Python programming problems (more
algorithmic, simpler structure). We use MBPP+ for h-e1 and h-m1
*characterization* only — to establish the mypy signal density on this
benchmark. h-e1 found 0% mypy error rate in MBPP+ failing solutions, which
predicts no Condition B benefit there and removes it from the primary
pass@1 comparison. The h-m3 MBPP+ Condition A run was started (122/378
tasks of seed=42) but not completed due to compute constraints.

**Arithmetic subset (h-z1):** 123 HumanEval+ problems selected by heuristic
keyword matching for arithmetic content (problems involving numeric
operations, mathematical relationships, number theory). Of these, 112 problems
receive valid Z3 specifications (spec validity rate: 91.1%), forming the h-z1
test set.

| Benchmark | Problems | Use | Mypy error rate in failures |
|-----------|----------|-----|-----------------------------|
| HumanEval+ | 164 | RQ1, RQ2, RQ3, RQ4 | 70% (21/30 failing) |
| MBPP+ | 378 | RQ1, RQ2 (characterization) | 0% (0/21 failing) |
| Arithmetic subset | 112 (valid specs) | RQ5 | N/A (subset) |

## Experimental Conditions

| Condition | Feedback per repair round | Maps to |
|-----------|--------------------------|---------|
| A | Execution output (pass/fail + stderr) | Baseline (Self-Debug style) |
| B | Execution output + mypy output | Treatment |
| C | Execution output + mypy output + Z3 CE (when found) | Z3 extension |

Condition A is the execution-only baseline established by Self-Debug
[Chen et al., 2023]. Conditions A and B differ by exactly one subprocess call
per repair round, ensuring that observed pass@1 differences are attributable
to the mypy feedback channel.

## Implementation Details

All experiments use **GPT-4o-mini** via the OpenAI API:

- **Initial generation:** temperature=0.8, max\_tokens=1024
- **Repair loop:** temperature=0.0, max\_tokens=2048
- **Seeds for h-m3:** {42, 123, 456}; other sub-hypotheses use seed=42

**mypy configuration:** `--ignore-missing-imports --no-strict-optional`;
timeout 30 seconds per call. These flags reduce false positives from missing
library stubs while preserving detection of structurally informative errors.

**Z3 configuration:** timeout 10 seconds per Z3 check; spec generated by
GPT-4o-mini from problem docstring; validated against EvalPlus ground-truth
tests before use.

**Repair rounds:** k=5. h-m1 establishes that mypy errors reach 0 by round 2;
k=5 captures full repair behavior and matches Self-Debug comparison conditions.

**Infrastructure:** EvalPlus test harness for pass@1 evaluation; Python 3.10;
mypy 1.x; Z3 Python API (`z3-solver`). Experiments implemented in Python with
a resume-based runner to handle interruptions.

## Evaluation Metrics

- **pass@1:** Fraction of problems where the final solution (after k=5 rounds)
  passes all EvalPlus test cases. For h-m3, reported per seed and as mean
  over 3 seeds. This is the primary metric for RQ4.

- **Spearman ρ:** Rank correlation between repair round index (1..5) and
  mean mypy error count across problems with ≥1 initial mypy error. Tests
  monotonic decrease (RQ2). Computed over n=20 eligible HumanEval+ problems.

- **Type-specificity differential:** delta\_type − delta\_non, where
  delta\_type = repair\_rate\_B − repair\_rate\_A on type-error problems (those
  with ≥1 initial mypy error in Condition B), and delta\_non on non-type-error
  problems. A positive differential supports the type-specificity hypothesis
  (RQ3).

- **Z3 CE rate:** Fraction of valid-spec arithmetic problems for which at
  least one Z3 counterexample was generated during any repair round (RQ5).

- **Z3 spec validity rate:** Fraction of generated Z3 specs that accept all
  EvalPlus ground-truth solutions for the corresponding problem.
