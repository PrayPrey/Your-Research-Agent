# Related Work

## LLM Repair Loops with Execution Feedback

The execution-feedback repair paradigm was established by Self-Debug
[Chen et al., 2023], which demonstrates that providing LLMs with their own
program output — captured stdout, stderr, and exception traces — enables
iterative repair that substantially improves pass@k over single-attempt
generation. Self-Debug operates on execution-only feedback, treating the
binary pass/fail signal augmented with error output as sufficient for repair.
This becomes our **Condition A baseline**: the de-facto standard that we test
against.

Reflexion [Shinn et al., 2023] extends the repair paradigm by having the LLM
generate verbal *reflections* on its failures before attempting repair. Verbal
reflection is unstructured: the LLM authors its own diagnostic narrative.
Our work tests a complementary hypothesis — that *external* structured
diagnostics (mypy output) provide signal beyond what the LLM can self-generate
or extract from execution output. The comparison is indirect: our Condition B
(execution+mypy) vs Condition A (execution-only) quantifies the marginal value
of one external structured channel over the execution signal that Reflexion
also uses as its starting point.

CodeT [Chen et al., 2022] and AlphaCode [Li et al., 2022] use execution
feedback at generation time (test case filtering, tournament selection) rather
than in iterative repair loops. These are orthogonal to our setting: we fix
the generation strategy and vary the repair feedback type.

**Gap we address:** Prior repair loop work treats feedback channel selection
as an engineering choice, not an experimental variable. Self-Debug, Reflexion,
and their successors do not ablate execution vs. execution+static-analysis.
We provide the first controlled comparison.

## Static Analysis in Code Generation and Repair

Static analysis tools have been integrated into LLM code generation systems,
but without controlled ablation of their marginal contribution. GitHub Copilot
and similar systems run linters and type checkers as post-processing filters,
not as feedback channels in repair loops. AlphaCode's competitive programming
pipeline incorporates program analysis, but the analysis is bundled with
execution feedback, making its independent contribution unquantifiable.

SWE-agent [Yang et al., 2024] uses a rich tool-use environment including bash
execution, file editing, and code analysis, embedded in an agent control loop
(ACI). The agent can invoke linters, but the ACI design makes it difficult to
isolate the contribution of any single feedback channel. We specifically avoid
this bundling: our experiment holds all factors constant except the feedback
type (execution-only vs. execution+mypy vs. execution+mypy+Z3).

LLM-based program repair (APR) surveys [Huang et al., 2023; Xia et al., 2023]
document that execution-based feedback — test case pass/fail, error messages —
is the dominant repair signal in the literature. Type-system feedback appears
in some systems (e.g., typed functional languages where type errors are
informative), but controlled comparison against execution-only baselines on
Python benchmarks is absent. Our work fills this gap.

**Gap we address:** Static analysis is routinely bundled with execution
feedback in production systems, but its isolated marginal contribution has not
been measured on standard Python code generation benchmarks.

## Evaluation Benchmarks: HumanEval and MBPP Variants

EvalPlus [Liu et al., 2023] introduces HumanEval+ and MBPP+ — enhanced
versions of HumanEval [Chen et al., 2021] and MBPP [Austin et al., 2021] with
substantially more test cases (generated by GPT-4, validated by experts).
We use HumanEval+ and MBPP+ as our primary evaluation benchmarks, following
the community's shift toward these harder variants.

A contribution of our work is a new structural observation about these
benchmarks: HumanEval+ and MBPP+ have dramatically different mypy error
profiles in GPT-4o-mini failing solutions (70% vs 0%). This finding is
orthogonal to EvalPlus's test strength contribution; it characterizes the
*type of failures* rather than the *number of test cases*. Prior work does not
report mypy error rates by benchmark, leaving this divergence unobserved.

## Formal Verification for Code Correctness

SMT-guided program repair [Kneuss et al., 2013; Nguyen et al., 2013] uses
constraint solvers to generate counterexamples that guide program repair in
classical APR systems. Recent work on LLM-guided Z3 spec generation [CITATION
NEEDED — recent 2023-2024 work on LLM+Z3 for program verification] explores
whether LLMs can generate formal specifications that are then checked by
constraint solvers. Our h-z1 sub-hypothesis is in this tradition: we test
whether LLM-generated Z3 specs can provide useful counterexample feedback for
repair, finding that while spec validity is high (91.1%), the counterexample
activation rate is low (16.1%) on our arithmetic HumanEval+ subset.

The neural-symbolic program synthesis literature (e.g., SKETCH [Solar-Lezama
et al., 2008], Rosette [Torlak & Bodik, 2014]) uses SMT solvers for
specification-guided synthesis. These systems assume a formal specification is
given; our setting uses LLM-generated specifications, which trades
completeness for automation. The 91.1% validity rate we observe establishes
that LLM-generated Z3 specs for simple arithmetic HumanEval+ problems are
mostly valid — a feasibility result for the automated specification generation
approach.

**Gap we address:** Prior work on LLM+Z3 program verification does not test
whether Z3 counterexample feedback improves LLM repair pass@1 in a controlled
comparison against execution-only and execution+mypy baselines.

## Repair Signal Quality and Specificity

A recurring question in the APR literature is whether more specific error
signals produce better repairs. [Xia & Zhang, 2023] study different error
representations for automated program repair, finding that structured error
information improves patch generation in some settings. In the LLM code
generation setting, [Olausson et al., 2023] analyze when LLM self-repair is
effective, noting that the repair signal's informativeness relative to the
error type matters.

Our h-m2 sub-hypothesis directly tests the type-specificity claim: if mypy
provides type-targeted signal, the improvement should concentrate on type-error
problems. The null result (90.9% repair rate under both conditions on type-error
problems) is consistent with the interpretation that execution feedback alone
is sufficient for the specific problem types that mypy detects on HumanEval+.
The broader improvement (+8.94pp) must come from a different channel, which
we identify as general diagnostic context enrichment — a mechanism not
previously studied in the LLM repair loop literature.
