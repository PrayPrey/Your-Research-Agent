# Agentic Property-Based Testing: Finding Bugs Across the Python Ecosystem

## Key Metadata
- **Authors:** Muhammad Maaz et al.
- **Year:** 2025
- **Venue:** NeurIPS 2025 Workshop (The 4th Deep Learning for Code Workshop)
- **Core Contribution:** An LLM-based coding agent that autonomously mines properties from Python code/docs, synthesizes and executes Hypothesis property-based tests, triages failures into actionable bug reports, and is evaluated at ecosystem scale (100 packages / 933 modules).

## Section Summaries

### Abstract
Property-based testing (PBT) is a lightweight formal method, typically imple-
mented as a randomized testing framework. Users specify the input domain for
their test using combinators supplied by the PBT framework, and the expected
properties or invariants as a unit-test function. The framework then searches for
a counterexample, e.g. by generating inputs and calling the test function. In this
work, we demonstrate an LLM-based agent which analyzes Python modules, in-
fers function-specific and cross-function properties from code and documentation,
synthesizes and executes PBTs, reflects on outputs of these tests to confirm true
bugs, and finally outputs actionable bug reports for the developer. We perform
an extensive evaluation of our agent across 100 popular Python packages. Of the
bug reports generated by the agent, we found after manual review that 56% were
valid bugs and 32% were valid bugs that we would report to maintainers. We
then developed a ranking rubric to surface high-priority valid bugs to developers,
and found that of the 21 top-scoring bugs, 86% were valid and 81% we would
report. The bugs span diverse failure modes from serialization failures to numerical
precision errors to flawed cache implementations. We reported 5 bugs, 4 with
patches, including to NumPy and cloud computing SDKs, with 3 patches merged
successfully. Our results suggest that LLMs with PBT provides a rigorous and
scalable method for autonomously testing software. Our code and artifacts are
available at: https://github.com/mmaaz-git/agentic-pbt.

### Introduction & Motivation
Property-based testing (PBT) checks general invariants over an input domain (e.g., non-negativity, commutativity) by searching for counterexamples via randomized input generation, and can be more robust than example-based tests at finding edge cases. However, PBT adoption is limited because identifying *meaningful* properties is hard and often demands substantial domain expertise and developer time. The paper targets this “property discovery bottleneck” by leveraging LLM code understanding to infer testable properties from documentation, signatures, and calling context—going beyond prior work that typically generates a single test for a single function. They introduce an *agentic* workflow that iterates: analyze code → propose properties (including cross-function/class) → write Hypothesis tests → run/triage failures → produce developer-ready bug reports.

### Methodology
The proposed system is **agentic property-based testing**, implemented as a **prompted coding agent** on top of **Anthropic’s Claude Code** (a terminal-based agent that can run shell commands and read/write files). The agent takes a **single target argument** pointing to a Python **file**, **module**, or **function** (e.g., `numpy`, `scipy.signal`, `requests.get()`). It then executes an explicit **6-step loop**:

1) **Analyze target type** (file vs module vs function) and locate relevant entry points.  
2) **Understand the target** by reading **documentation**, **function signatures**, **source code**, and surrounding context (including *callers* to infer intended input domains/constraints).  
3) **Propose properties** grounded in evidence from step (2). The prompt emphasizes “high-value” properties such as:
   - **Invariants** (e.g., output constraints like non-negativity),
   - **Round-trip properties** (serialize/deserialize; encode/decode),
   - **Metamorphic relations** (behavior under transformations),
   - **Cross-function relations**, e.g. commutativity: \( f(g(x)) = g(f(x)) \).
4) **Write PBTs** as executable **Hypothesis** tests (Python), using strategy combinators to generate diverse inputs over the inferred domain, and embedding the property as assertions in a `pytest` test function.  
5) **Execute & triage** by running `pytest`. For failures, the agent uses a **reflection rubric** to decide whether the counterexample indicates a *true bug* vs (i) incorrect property, (ii) overly broad input domain, or (iii) intended behavior. If judged a false alarm, it iterates: refine the property, narrow strategies, or add assumptions; if tests pass, it checks whether the test is *meaningful* (not vacuous).  
6) **Report bugs** by writing a standardized **Markdown bug report** containing: (a) summary, (b) the Hypothesis PBT that exposed the issue, (c) minimal reproducer script, (d) justification “why this is a bug,” and optionally (e) a patch.

Key design choices to reduce false positives include: maintaining a **to-do list** across the multi-step cycle; prioritizing **few, strongly-evidenced** properties; careful reflection on failures; and granting broad autonomy so the agent can choose which functions/modules to probe and when to stop. Notably, there is **no model training** or gradient-based optimization described; the “method” is an **orchestrated prompting + tool-use** workflow coupled to Hypothesis-driven randomized counterexample search.

### Experiments & Results
**Evaluation corpus.** The authors curate **100 Python packages** using three sampling strategies:
- **15 standard library** modules: `json, pathlib, collections, itertools, functools, datetime, re, os, urllib, statistics, decimal, base64, uuid, html, csv`.
- **15 third-party PyPI** packages: `numpy, pandas, requests, flask, sqlalchemy, matplotlib, scipy, beautifulsoup4, pydantic, fastapi, django, tornado, keras, httpie, black`.
- **70 random** packages sampled from the **top 5,000 PyPI packages by downloads** (diverse domains; list released with code).

**Targeting / scale.** For each package, the agent is run on the **main module** (e.g., `bs4`) and **all submodules one level deep** (e.g., `numpy.linalg`). Total: **933 modules** tested.

**System setup.** LLM: **Claude Opus 4.1**. Each run executes in an **isolated virtualenv** containing the target package + dependencies + **Hypothesis**, with permissions to read/write the working directory, read installed source, run `python`/`pytest`, and access the internet. Runs were parallelized up to **N = 20** concurrent agents. Hardware: **RunPod Ubuntu 20.04**, **8 vCPUs**, **16 GB RAM**, **50 GB disk**.

**Bug report validation protocol.** Because full ground-truth is infeasible across 100 heterogeneous codebases, they combine LLM scoring + human review:
- Build an **initial scoring rubric** to filter obvious false alarms; have Claude grade reports.
- Randomly sample **n = 50** bug reports from the **top 80%** by rubric score.
- Two authors independently judge each report on two questions: (1) “valid bug?” (2) “valid and worth reporting to maintainers?” Disagreements are discussed to consensus. Inter-rater agreement: **κ = 0.31**.
- Using insights, they create a **final rubric** scoring reports **0–15**; have Claude grade all reports; then **manually review all 15/15** reports.

**Main outcomes (including cost/scale).** Across 933 modules, the agent generated **984 bug reports**, flagging issues in **786 modules (84.2%)**, averaging slightly over **1 report/module**. Total runtime: **136.6 hours** (**82 min/package**, **8.8 min/module**). Total API cost: **$5,474.20** (**$54.74/package**, **$5.87/module**, **$5.56/report**). Usage: ~**110 turns** per run; **2.21B tokens total** (input+output), i.e. **2.37M/module**.

**Manual-review validity rates.** From the sampled-and-consensus human review:
- **56.0%** were **valid bugs** (95% CI: **[42.2%, 69.8%]**).
- **32.0%** were **valid and worth reporting** (95% CI: **[19.1%, 44.9%]**).
They also report a false discovery rate CI: **95% CI [30.2%, 57.8%]** (as stated in limitations).

**Ranking efficacy.** Under the final 0–15 rubric, among the **21 top-scoring** reports:
- **18/21 (86%)** were valid bugs,
- **17/21 (81%)** were valid and worth reporting.

**Concrete bugs reported upstream (examples + property forms).**
- **NumPy (`numpy.random`)**: Property “Wald distribution should only return non-negative samples.” Bug: negative samples due to **catastrophic cancellation**. **Acknowledged; patch merged (PR #29609)**.
- **aws-lambda-powertools (`slice_dictionary`)**: Property “chunks recombine to original dict.” Bug: repeats first chunk (iterator not incremented). **Acknowledged; patch merged (PR #7246)**.
- **cloudformation-cli-java-plugin (`item_hash`)**: Property “different inputs → different hashes.” Bug: list inputs hash to `hash(None)` due to in-place `.sort()` returning `None`. **Patch submitted (PR #1106)**.
- **tokenizers (`EncodingVisualizer.calculate_label_colors`)**: Property “returns valid HSL format.” Bug: missing closing parenthesis. **Acknowledged; patch merged (PR #1853)**.
- **python-dateutil (`easter`)**: Property “Easter should be on Sunday.” Reported as bug; maintainers say behavior is intended under Julian calendar semantics, but confusing. **Issue filed (#1437)**.

### Discussion & Conclusion
The main takeaway is that combining LLM agent tool-use with Hypothesis PBT can uncover diverse, real-world bugs (numerical stability, serialization, business logic, formatting) at scale across widely used Python packages. The authors argue the approach is cost-effective—using their manual validity estimate, they compute roughly **$9.93 per valid bug** (derived from $5.56/report and 56% validity)—but emphasize that developer expertise can target runs to reduce wasted effort. Limitations include incomplete manual validation of all 984 reports and **intent ambiguity** (some “violations” are deliberate design choices), motivating better specification/grounding and human-in-the-loop triage for production use.

## Key Contributions
- **Agentic PBT pipeline:** A multi-step coding-agent workflow that (i) reads code/docs, (ii) infers function-specific and cross-function properties, (iii) generates and runs Hypothesis PBTs, (iv) triages failures via reflection, and (v) emits standardized, actionable bug reports (optionally with patches).
- **Ecosystem-scale evaluation:** The largest systematic study in the paper of LLM-driven property-based testing across the Python ecosystem: **100 packages / 933 modules / 984 reports**, with runtime, token, and dollar-cost accounting.
- **Bug-report ranking & empirical precision:** A rubric-based scoring/ranking method that surfaces higher-priority reports, achieving **86% validity** among the **top 21** scored reports, plus demonstrated real-world impact via **5 upstream reports** (with **3 patches merged**).

## Potential Relevance
This paper is useful as evidence that *iterated* LLM agent loops (not single-shot generation) can make PBT practical by discovering properties from context and refining tests after failures—suggesting a research direction around automated property mining + counterexample-guided spec repair. The reported precision/recall tradeoffs (56% validity overall vs 86% among top-ranked) and operational metrics (tokens, turns, dollars, runtime) provide concrete baselines for hypotheses about cost-effective autonomous auditing. The limitations around “intent ambiguity” also motivate hypotheses about integrating richer specifications (types/contracts), maintainer feedback, or semantic documentation alignment to reduce false alarms.
