## Lessons from Previous Attempts

### What Was Tried Before

**Attempt 1 (archived 20260804T035114):** Post-training alignment via execution feedback RL on existing benchmarks (HumanEval, MBPP, SWE-bench-lite). Hypothesis H-E1 (EXISTENCE) tested signal density feasibility on APPS interview problems with Qwen2.5-Coder-7B (G=8).

### Why It Failed

**Failure Record: H-E1 — Phase 4 MUST_WORK gate PIVOT**

Three compounding root causes:
1. **APPS harness environment incompatibility:** `testing_util.reliability_guard()` blocks subprocess execution in nested agent context — all unit tests returned False/error, making test_pass_rate signal completely unusable.
2. **Compile rate too low on APPS interview difficulty:** Mean compile rate 11.6%; only 11/200 problems in the [0.15, 0.45] signal density window. Extrapolation: ~110 compile-passing problems total — below the 500-problem EXPLORE threshold.
3. **Joint window constraint unachievable:** Requiring BOTH compile_rate AND test_pass_rate in [15%, 45%] simultaneously yielded 0/200 matching problems. The model (Qwen2.5-Coder-7B) simply cannot generate compilable code reliably on APPS interview-level difficulty.

### How This New Direction Avoids Those Pitfalls

| Past Failure | New Direction Fix |
|---|---|
| APPS harness subprocess isolation issue | Use HumanEval/MBPP — standard Python function evaluation, no subprocess isolation issues |
| Joint compile+test signal window constraint | Use single signal: execution correctness (pass@1 binary) as data filter criterion |
| RL post-training complexity (needs training runs) | Switch to SFT data filtering — simpler, directly testable with existing open datasets |
| APPS interview difficulty too hard for model | HumanEval/MBPP are calibrated difficulty; model pass rates fall in measurable range |
| Signal density feasibility scan as hypothesis | Hypothesis is now about SFT data quality comparison — directly measurable, no feasibility scan needed |

## Research Question Development

### Initial Question

Does filtering code SFT training data by execution correctness (selecting only compilable and test-passing examples) improve code LLM fine-tuning performance on standard benchmarks compared to unfiltered SFT?

### Refined Question

Does applying execution-based filtering (retaining only examples that compile and pass unit tests) to an existing open-source code training corpus improve supervised fine-tuning (SFT) performance of a code LLM on HumanEval and MBPP, compared to SFT on the unfiltered corpus of the same token budget — and does the degree of filtering strictness (compile-only vs. compile+test) affect the magnitude of improvement?

### Detailed Sub-Questions

1. Does SFT on execution-filtered code data (compile + test pass) outperform SFT on unfiltered data of equal token count on HumanEval pass@1 and MBPP pass@1?
2. Is compile-only filtering sufficient, or does adding unit-test-pass filtering provide additional gain beyond compile-only filtering?
3. Does the benefit of execution filtering scale with the filtering ratio (e.g., 10% retained vs. 30% retained vs. 50% retained) — is there an optimal filtering threshold?
4. Does execution-filtered SFT outperform length-matched random SFT subsampling, isolating the quality signal from the data-quantity reduction effect?
5. Do gains from execution-filtered SFT generalize across model sizes (e.g., 1B vs. 7B parameter code LLMs from the same family)?

## Session Insights

### Key Discoveries

ROUTE_TO_0 recovery generated a fundamentally different approach by pivoting from RL post-training to SFT data filtering. Key insight: H-E1's failure was caused by three compounding factors — APPS harness incompatibility, model capability mismatch with APPS interview difficulty, and overly strict joint signal window. The new direction eliminates all three by: (1) using HumanEval/MBPP for evaluation (no harness issues), (2) using execution filtering on training data rather than live inference-time signals, and (3) replacing the joint window constraint with a simple binary filter. The research question is now directly measurable with a standard SFT training run + benchmark evaluation loop.

### Areas for Further Exploration

Other DL4C-compatible directions not pursued (may be viable for future pipelines if this direction also fails):

- Execution-feedback for agentic code generation (SWE-bench) — larger scope, needs SWE-bench agent infrastructure
