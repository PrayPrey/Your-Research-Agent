## Section Summaries

### Abstract
While experimental reproduction remains a pillar of the scientific method, we observe that the software best practices supporting the reproduction of machine learning (ML) research are often undervalued or overlooked, leading both to poor reproducibility and damage to trust in the ML community. We quantify these concerns by surveying the usage of software best practices in software repositories associated with publications at major ML conferences and journals such as NeurIPS, ICML, ICLR, TMLR, and MLOSS within the last decade. We report the results of this survey that identify areas where software best practices are lacking and areas with potential for growth in the ML community. Finally, we discuss the implications and present concrete recommendations on how we, as a community, can improve reproducibility in ML research.

### Introduction & Motivation
ML research is empirically grounded and therefore depends critically on software artifacts (code, environments, execution procedures) to enable independent testing of published claims. Despite widespread code release norms, many repositories lack basic software engineering (SWE) practices that make results repeatable across machines and over time (e.g., dependency pinning, tests, packaging, licensing), undermining trust and slowing cumulative progress. The paper argues that reproducibility discussions often stop at “is code available?” but should extend to “is the code usable, verifiable, and maintainable?” To close this gap, the authors (i) formalize a set of automatically measurable SWE best-practice indicators (primarily Python-centric, reflecting ML’s ecosystem) and (ii) quantify their adoption at scale across major ML venues from 2018–2025, then (iii) propose practical, reviewer-usable recommendations to improve the situation without overburdening authors.

(2) **Bulk-download PDFs**: use custom scrapers for proceedings pages when available; otherwise use the **OpenReview API** (e.g., ICML 2025 at crawl time). Proceedings scraping uses **BeautifulSoup** to collect paper links by filtering URLs ending in “pdf”. (5) Compute **adoption rates** as the percentage of repositories containing each indicator, plotted over time (2018–2025) and compared across venues, with **MLOSS as a “software-forward” baseline**.

### Discussion & Conclusion
The study concludes that “code availability” is insufficient for reproducibility: missing licensing, incomplete dependency specs, low packaging, and weak testing/automation collectively make many ML results hard to rerun or extend. The authors recommend lightweight, community-level incentives (especially reviewer/venue checklists) while acknowledging practical constraints (time pressure, lack of SWE training/mentorship, and risk of overly rigid enforcement discouraging code release). Overall, they argue that adopting SWE best practices is a long-run efficiency gain (less technical debt, easier onboarding, fewer silent bugs) and would strengthen ML’s empirical foundation.

## Key Contributions
- **(1) Operationalization of reproducible-ML SWE “best practices” as automatically measurable repository signals (with a Python-centered but conceptually language-agnostic framing).**  
  The paper’s main technical contribution is not a new ML algorithm but a concrete *measurement design*: it turns common SWE recommendations into a checklist of **observable, machine-detectable artifacts** in GitHub repositories, enabling large-scale auditing. The reviewed practice set spans: (i) **Licensing** (presence of LICENSE/COPYING) as a prerequisite for legally unambiguous reuse; (ii) **Onboarding documentation** via README as the first-stop “how to run” surface; (iii) **Formatting/linting/type checking** (e.g., Flake8 configs, Ruff often via pyproject.toml, MyPy) as maintainability and defect-prevention mechanisms; (iv) **Dependency enumeration** via requirements.txt / environment.yml and the ecosystem trend toward standardized metadata/locking (PEP-621 `pyproject.toml`, PEP-751 `pylock.toml`), motivated by version-sensitive behavior (e.g., PyTorch randomness differences across versions); (v) **Packaging** (src layout, setup.py/setup.cfg, pyproject.toml) to prevent copy-paste reuse and enable pip-installable modularization; (vi) **Testing** (tests/ directories, pytest/unittest) to codify assumptions and guard against regressions/technical debt; and (vii) **Automation** (tox/nox + CI via `.github/workflows`, pre-commit hooks, Makefile) to run checks consistently. Importantly, the authors explicitly restrict attention to indicators that can be measured automatically at scale (presence/absence), acknowledging that this is a proxy for quality rather than a semantic evaluation of correctness or completeness.

- **(2) A scalable crawl-and-audit pipeline for linking ML papers to code repositories and computing longitudinal adoption trends across major venues (2018–2025), with an explicit “software venue” baseline.**  
  The methodological contribution is a **repeatable data pipeline** that starts from ML proceedings/journal papers and ends in structured adoption statistics. Key design choices include: selecting **major ML conferences** (NeurIPS, ICML, ICLR, AISTATS) plus **journals** (TMLR, MLOSS), and using **MLOSS** as a meaningful baseline because it is inherently oriented toward reusable software (so higher SWE practice adoption is expected). The pipeline integrates multiple acquisition routes (scraping proceedings pages vs OpenReview API), PDF parsing (pdfx + custom heuristics) to extract GitHub links, and repository scanning that is robust to common naming variants (README.md/README.rst, LICENSE/COPYING, etc.). The result is a venue- and year-indexed time series of adoption rates that can detect changes around community interventions (e.g., NeurIPS code guide introduced in 2020, with the authors observing “solid positive trends” in dependency documentation thereafter). The paper also adds an important normalization step: because many practices are Python ecosystem-specific, it estimates Python prevalence first and then filters to Python repos, showing that Python usage exceeds **80% since 2021**, making Python-targeted improvements high leverage. Finally, the authors release analysis code (**https://github.com/BonnBytes/ml-swe-analysis**) explicitly to enable periodic refresh/extension—positioning the work as an evolving measurement instrument rather than a one-off descriptive snapshot.

- **(3) Empirical identification of the largest reproducibility bottlenecks (beyond README availability) and a concrete, reviewer-friendly action checklist that balances rigor with feasibility.**  
  The empirical results highlight a gap between superficial openness and practical reproducibility. Even though README adoption is near universal, several *high-impact* reproducibility enablers remain under-adopted: (i) **Licensing** is incomplete and appears to stagnate at **~50–80%**, implying that a substantial fraction of ML code is reused without clear legal permission (or at least without explicit terms); (ii) **Dependency specification** remains insufficient—e.g., at **ICML 2024, <50%** of repos provide requirements/environment files—despite strong evidence that version drift can change results; (iii) **Lockfiles** (e.g., uv.lock, poetry.lock, pylock.toml) are extremely rare (**~0–2.5%**), limiting exact environment recreation; (iv) **Packaging** practices are only partially adopted (setup.py roughly **20–40%**, pyproject.toml rising but not universal), reinforcing copy-paste reuse and making composition across projects harder; (v) **Testing and automation** are the starkest weaknesses, with tests folders in roughly **~25%** of repos and an estimate that **~75%** operate without automated testing/workflow checks. In response, the paper proposes a concrete checklist for authors/reviewers (license, README, dependency docs + ideally `pylock.toml`, packaging for installability, containerized/isolated tests via tox/nox, fixed RNG seeds, automated code checks, and ideally a “single command” to rerun experiments). Crucially, the authors temper enforcement: they note legitimate exceptions (e.g., small illustrative notebooks for theory work) and warn that over-aggressive “test crusades” could backfire by incentivizing code withholding. This “measured rigor” framing is itself a contribution: it turns SWE practices into actionable norms while explicitly accounting for ML’s deadline-driven publication culture and uneven SWE mentorship.

## Potential Relevance
This paper provides a ready-made **measurement framework and artifact checklist** that can be reused to test hypotheses about how repository quality signals (licenses, environment locking, packaging, CI/tests) correlate with downstream outcomes like successful reproduction rates, community uptake, or citation impact. Its findings also suggest concrete intervention points—e.g., requiring dependency specs/lockfiles and minimal CI checks—that could be experimentally evaluated at a venue or lab level to quantify reproducibility gains. Finally, the MLOSS-vs-TMLR and conference trend comparisons offer a baseline for designing “software-forward” policy changes and for benchmarking new tooling (cookiecutter templates, automated packaging/locking workflows) against observed adoption ceilings.
