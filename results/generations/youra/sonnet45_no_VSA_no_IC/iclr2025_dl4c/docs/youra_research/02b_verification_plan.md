## 1. Main Hypothesis & Baselines

### 1.1 Core Statement

Under small model capacity constraints (350M-1B parameters) and existing code generation benchmarks (HumanEval, MBPP), if we train models with execution feedback at varying granularity levels (binary pass/fail, error-type vocabulary, error+stack-trace), then lightweight feedback (binary or error-type) achieves ≥80% relative retention of rich feedback gains AND ≥8 pp absolute improvement over supervised fine-tuning baseline, because small models have limited representational capacity to utilize high-dimensional supervision signals, and lower-granularity feedback provides concentrated, noise-reduced learning signals.

### 1.2 Alternative Hypothesis (H0)

There is no significant difference in pass@1 performance between models trained with binary feedback versus error-type feedback versus error+stack-trace feedback, controlling for training compute and model capacity.

### 1.3 Experimental Setup (from Phase 2A)

| Component | Selection | Justification |
|-----------|-----------|---------------|
| **Dataset** | HumanEval + MBPP (standard) | HumanEval provides algorithm-focused problems with comprehensive test suites (hypothesized to enable binary feedback sufficiency). MBPP provides entry-level problems with weaker test coverage (hypothesized to benefit from error-type feedback). Testing both benchmarks validates coverage-granularity hypothesis. |
| **Model** | CodeGen-350M-mono + StarCoder-1B | 350M and 1B parameter models fit 'small model' scope. Both sizes avoid capacity saturation on MBPP (current SOTA ~60-70% for 1B) while testing non-linear capacity-feedback relationship. |

**Dataset Details:**
- Source: HumanEval: OpenAI (Austin et al. 2021, 164 problems). MBPP: Google (974 problems)
- Path: HumanEval: https://github.com/openai/human-eval | MBPP: https://github.com/google-research/google-research/tree/master/mbpp

**Model Details:**
- Type: Pretrained code generation models
- Source: CodeGen (Salesforce), StarCoder (BigCode), or phi-2 (Microsoft) — publicly available

### 1.4 Baseline Methods (for Phase 5 comparison)

| Method | Performance | Dataset |
|--------|-------------|---------|
| CoCoS (Cho et al. 2025) - RL-based self-correction | +35.8% on MBPP pass@1 | MBPP |
| RLVR (Skopin et al. 2026) - Unit test feedback | +13 pp on MBPP pass@1 | MBPP |
| CodeRL+ (Jiang et al. 2025) - Variable-level execution semantics | +4.6% on pass@1, +15.5% on code-reasoning | HumanEval, MBPP |

### 1.5 Key Assumptions

| ID | Assumption | Evidence | If Violated |
|----|------------|----------|-------------|
| A1 | Natural error distributions (as generated by baseline models) are representative of deployment error patterns | Baseline models (SFT on code corpora) generate realistic code with realistic failure modes. Frequency analysis on 1000 samples can validate representativeness. | If deployment errors differ significantly from training errors (e.g., rare edge cases dominate production), feedback granularity optimized for training distribution may underperform in practice. |
| A2 | Bits-per-problem is a valid proxy for information content in feedback signals | Information theory: entropy of categorical distribution = log₂(vocabulary size). Error-type vocabulary of 5 ≈ 2.3 bits. Stack trace adds depth buckets (10 levels) ≈ 3.3 bits. | If semantic meaning (not entropy) drives learning, bit-counting is misleading. For example, 1 bit of 'error vs correct' may carry more semantic value than 3 bits of 'stack trace depth'. |
| A3 | Branch coverage is a valid proxy for test suite quality | Standard software engineering metric. Higher branch coverage generally indicates more thorough testing of code paths. | If semantic test quality (edge case detection, assertion diversity) matters more than coverage percentage, branch coverage won't explain feedback-type advantages. Would need additional metrics (mutation testing, assertion types). |
| A4 | SFT baseline represents 'no execution feedback' condition fairly | SFT trains on (problem description, reference solution) pairs without test outcomes. Standard baseline in code generation literature (CodeRL, CoCoS, RLVR all use SFT as baseline). | If SFT implicitly learns execution patterns from training corpus (e.g., common error patterns in code comments), baseline may already contain weak execution feedback signal, compressing observed gains. |
| A5 | Model capacity saturation does not occur on HumanEval/MBPP for 350M-1B models | Current SOTA on MBPP for 1B models ~60-70% (from CoCoS, RLVR papers), leaving headroom. HumanEval harder, more headroom. | If 1B models hit ~70% ceiling on MBPP regardless of feedback type, ceiling effects obscure feedback differences. Mitigation: use HumanEval Pro (harder benchmark) if saturation observed. |

### 1.6 Research Gap & Novelty

Establishes execution feedback granularity as an efficiency optimization problem (gain-per-bit) rather than a capability maximization problem (richest signal available). No prior work systematically studies granularity tradeoffs for small models <1B parameters.

**Key Innovation:** Dual-threshold evaluation (absolute + relative gain) prevents weak-but-technically-sufficient results. Efficiency metric (pp-gain / bits-per-problem) provides new lens for comparing alignment methods beyond raw performance. Causal test of coverage-granularity relationship via measured branch coverage (not assumed).

**Differentiation from Prior Work:**
- CodeRL+ focuses on RICHER feedback (variable traces) for larger models. This work explores MINIMAL sufficient feedback for small models, opposite direction.
- CoCoS uses accumulated trajectory rewards (opaque about granularity). This work explicitly ablates granularity levels and measures efficiency.
- Feedback Over Form (McAndrews 2026) compares feedback vs NO feedback. This work assumes feedback is valuable, asks WHICH feedback granularity is optimal.

### 2.2 Hypothesis Specifications

#### H-E1: Binary Feedback Achieves Dual-Threshold Sufficiency

**Type:** EXISTENCE
**Statement:** Under small model capacity constraints (350M-1B parameters), if we train models with binary pass/fail feedback on HumanEval, then binary feedback achieves ≥8 pp absolute improvement over SFT baseline AND ≥80% relative retention of error-type feedback gains, because binary feedback provides sufficient learning signal when test suites are comprehensive.

**Variables:**
- IV: Feedback granularity (binary vs error-type vs SFT baseline)
- DV: Pass@1 improvement (percentage points over baseline)
- CV: Model size (350M, 1B), training compute (3-5 GPU-hrs), base checkpoint

**Success Criteria:**
- Binary achieves ≥8 pp absolute improvement (e.g., SFT=40% → Binary≥48%)
- Binary achieves ≥80% relative retention: (Binary - SFT) / (Error-type - SFT) ≥ 0.8

**Gate:**
- Type: MUST_WORK
- If Fail: Existence hypothesis refuted → lightweight feedback insufficient → re-evaluate main hypothesis

**Prerequisites:** None

**Verification Protocol:**
Train 350M and 1B models with three conditions: (1) SFT baseline (no execution feedback), (2) Binary feedback (1 bit: pass/fail), (3) Error-type feedback (2.3 bits: top-5 Python exceptions). Evaluate on HumanEval using BigCode harness. Compute absolute improvement (Binary - SFT) and relative retention (Binary - SFT) / (Error-type - SFT). Check dual threshold: ≥8 pp AND ≥80%. Run 3 seeds per condition, report mean ± std. Statistical test: two-sample t-test with Bonferroni correction (α=0.0167).

---

#### H-M1: Capacity Limits Constrain High-Dimensional Feedback Utilization

**Type:** MECHANISM
**Statement:** Under small model capacity constraints (350M-1B parameters), if we compare feedback efficiency (pass@1 gain per bit) across granularity levels, then efficiency decreases as feedback richness increases (binary > error-type > error+trace), because small models cannot extract actionable gradients from high-dimensional supervision signals and suffer from noise-dominated learning.

**Variables:**
- IV: Feedback granularity (binary 1 bit, error-type 2.3 bits, error+trace 5.6 bits)
- DV: Feedback efficiency (pass@1 improvement / bits-per-problem)
- CV: Model size, training compute, error distribution (natural)

**Success Criteria:**
- Monotonic decrease in efficiency: Binary ≥7 pp/bit, Error-type 4-6 pp/bit, Error+trace 2-3 pp/bit
- Statistical significance in pairwise comparisons (binary vs error-type, error-type vs trace)

**Gate:**
- Type: MUST_WORK
- If Fail: Capacity constraint mechanism invalid → richer feedback may be equally or more efficient → challenges efficiency frontier hypothesis

**Prerequisites:** H-E1

**Verification Protocol:**
Extend H-E1 experiment with error+trace condition (error type + stack trace depth buckets). Compute efficiency = (pass@1 - SFT) / bits-per-problem for each condition. Binary: gain / 1.0 bits. Error-type: gain / 2.3 bits. Error+trace: gain / 5.6 bits. Plot efficiency frontier. Check monotonic decrease via pairwise t-tests. Control for total training compute (same GPU-hours per condition) to isolate information efficiency from compute efficiency.

---

#### H-M2: Low-Granularity Feedback Concentrates Signal With Reduced Noise

**Type:** MECHANISM
**Statement:** Under small model capacity constraints (350M-1B parameters), if we analyze learning dynamics during training with different feedback granularity levels, then low-granularity feedback (binary, error-type) shows faster convergence and lower gradient variance compared to high-granularity feedback (error+trace), because concentrated supervision signals have higher signal-to-noise ratio in gradient updates.

**Variables:**
- IV: Feedback granularity level
- DV: Training convergence rate (eval loss decrease per epoch), gradient variance (std of batch gradients)
- CV: Model architecture, batch size, learning rate schedule

**Success Criteria:**
- Binary and error-type show ≥20% faster convergence (epochs to 90% of final performance) than error+trace
- Binary and error-type show ≥30% lower gradient variance than error+trace

**Gate:**
- Type: MUST_WORK
- If Fail: Signal concentration mechanism invalid → challenges noise-reduction rationale for lightweight feedback

**Prerequisites:** H-E1

**Verification Protocol:**
During training runs from H-E1/H-M1, log per-epoch eval loss and per-batch gradient statistics. Compute convergence metric: epochs required to reach 90% of final eval loss. Compute gradient variance: mean std across all parameters per batch, averaged over training. Compare binary/error-type vs error+trace using t-tests. Visualize learning curves and gradient variance trajectories. Control for total training steps (same number of gradient updates per condition).

#### H-M3: Test Coverage Quality Moderates Feedback Granularity Requirements

**Type:** MECHANISM
**Statement:** Under small model capacity constraints (350M-1B parameters), if we measure test coverage quality (branch coverage %) for HumanEval and MBPP problems and correlate with per-problem feedback-type advantage, then test coverage explains ≥60% of variance (Pearson r ≥ 0.77) in feedback-type advantage (error-type gain over binary), because comprehensive test suites enable binary sufficiency while weak coverage benefits from error-type semantic hints.

**Variables:**
- IV: Test coverage quality (branch coverage % per problem)
- DV: Feedback-type advantage (error-type pass@1 - binary pass@1, per problem)
- CV: Problem difficulty, model size

**Success Criteria:**
- Pearson correlation r ≥ 0.77 (R² ≥ 0.6) between coverage and feedback advantage
- HumanEval and MBPP differ by ≥10 pp average coverage (sufficient variance to test hypothesis)

**Gate:**
- Type: SHOULD_WORK
- If Fail: Coverage moderation hypothesis invalid → feedback granularity requirements may depend on other factors (problem difficulty, solution complexity) not test coverage

**Prerequisites:** H-E1, H-M2

**Verification Protocol:**
Measure branch coverage for all HumanEval (164) and MBPP (974) problems using coverage.py on reference solutions. Run training with binary and error-type feedback, evaluate per-problem pass@1. Compute per-problem advantage: error-type_pass@1 - binary_pass@1. Correlate coverage with advantage using Pearson correlation. Check r ≥ 0.77. Perform robustness checks: (1) control for problem difficulty via baseline SFT performance, (2) report statement and path coverage as secondary metrics, (3) stratify by benchmark (HumanEval vs MBPP) to test coverage difference hypothesis.

## 4. Risk Analysis

### 4.1 Risk Summary

| Risk ID | Assumption | Probability | Impact | Mitigation |
|---------|------------|-------------|--------|------------|
| R1 | A1: Natural error distribution representative | Medium | High | Stratified per-error-type analysis, frequency reporting |
| R2 | A2: Bits-per-problem valid information proxy | Medium | High | Dual control: bit-matched AND compute-matched experiments |
| R3 | A3: Branch coverage valid test quality proxy | Low | Medium | Multiple metrics (branch/statement/path), acknowledge proxy limits |
| R4 | A4: SFT baseline fair (no execution feedback in corpus) | Low | Medium | Corpus token analysis for execution-related patterns |
| R5 | A5: No model saturation on benchmarks | Medium | High | HumanEval Pro fallback, ceiling detection metrics |

### 4.2 Mitigation Strategies

**R1 - Error Distribution Skew:**
- **Strategy:** Report error type frequencies from baseline generations. Perform stratified analysis: report per-error-type gains separately (TypeError, NameError, IndexError, ValueError, AttributeError).
- **Rationale:** If 90% of errors are TypeError, error-type feedback degenerates to near-binary. Stratified analysis detects this and allows interpretation.

**R2 - Information Proxy Validity:**
- **Strategy:** Run dual control experiments: (1) bit-matched (binary 1 bit, error-type 2.3 bits, trace 5.6 bits), (2) compute-matched (same GPU-hours, adjust training steps to equalize compute).
- **Rationale:** If semantic value matters more than entropy, bit-matched and compute-matched experiments will show different rankings. Dual control resolves thesis-antithesis tension.

**R3 - Coverage Proxy Limits:**
- **Strategy:** Report multiple coverage types (branch, statement, path) for all problems. Acknowledge in limitations that coverage % is proxy for semantic test quality.
- **Rationale:** Multiple metrics provide robustness check. If all three correlate with feedback advantage, coverage hypothesis strengthened. If not, identifies proxy limitations.

**R4 - Baseline Contamination:**
- **Strategy:** Analyze SFT training corpus (CodeGen/StarCoder pretraining data) for execution-related tokens (keywords: "error", "exception", "traceback", "assert"). Report frequency.
- **Rationale:** If corpus contains high frequency of execution traces (e.g., in code comments), SFT may implicitly learn weak execution feedback. Corpus analysis quantifies contamination risk.

**R5 - Model Saturation:**
- **Strategy:** Monitor per-condition performance on MBPP. If any condition exceeds 68% pass@1 (approaching 70% ceiling from CoCoS), switch to HumanEval Pro (harder benchmark with more headroom).
- **Rationale:** Ceiling effects compress variance between conditions. HumanEval Pro provides escape hatch if saturation detected.

## 5. Dialectical Analysis

### 5.1 Thesis

**Claim:** Lightweight execution feedback (binary or error-type) achieves ≥80% of rich feedback gains for small models (350M-1B params) because capacity constraints prevent effective utilization of high-dimensional signals.

**Premises:**
1. Small models have limited representational capacity to extract gradients from high-dimensional feedback
2. Binary/error-type feedback concentrates supervision into fewer dimensions, reducing noise
3. Test coverage quality moderates granularity requirements
4. CoCoS/RLVR demonstrate small models improve with execution feedback
5. Information-theoretic efficiency (gain-per-bit) provides valid comparison metric

**Strengths:**
- Builds on established small model capacity limits literature
- Efficiency metric provides novel evaluation lens beyond raw performance
- Dual-threshold prevents weak sufficiency claims
- 40 GPU-hour budget is feasible for single-GPU researchers

**Weaknesses:**
- Bits-per-problem may not capture semantic value differences
- Natural error distributions may heavily skew toward frequent types
- Branch coverage is proxy for test quality, not complete measure
- Only tests 2 model sizes (350M, 1B) - phase transitions at other scales unknown

### 5.2 Antithesis

**Claim:** There is no significant difference in pass@1 performance between binary, error-type, and error+trace feedback for small models - any observed differences are within noise, and richer feedback may actually perform better when properly controlled for information content.

**Premises:**
1. Semantic information content matters more than entropy - pass/fail bit may be less informative than error type categorization
2. Small models in CodeRL/RLVR studies used trajectory-level rewards (richer than binary), suggesting capacity for complex signals
3. If SFT baseline already contains weak execution feedback from corpus, binary feedback adds minimal new information
4. Natural error distributions heavily skewed (TypeError dominant) means error-type feedback degenerates to near-binary in practice
5. Branch coverage correlation with feedback advantage may be spurious - both could correlate with problem difficulty rather than causal relationship

**Strengths:**
- Challenges bit-counting assumption directly - semantic value vs entropy is testable
- Points to baseline contamination risk (SFT corpus analysis needed)
- Identifies potential confound (problem difficulty) in coverage correlation

**Weaknesses:**
- CodeRL/RLVR evidence is indirect - those studies didn't ablate granularity
- Doesn't explain why capacity limits wouldn't bind for small models
- Natural distribution skew is acknowledged risk with mitigation (stratified analysis)

### 5.3 Synthesis

**Claim:** The hypothesis is testable and valuable regardless of outcome: confirming thesis validates efficiency optimization for resource-constrained settings; confirming antithesis reveals semantic information matters more than entropy, guiding future feedback design toward quality over compression.

**Resolution Path:**
1. Dual validation approach (bit-controlled AND compute-controlled experiments) directly tests thesis vs antithesis
2. Stratified per-error-type analysis detects if error-type feedback degenerates to binary in practice
3. Coverage correlation + problem difficulty controls distinguish causation from confound
4. SFT corpus analysis tests baseline contamination hypothesis
5. Even null result (all feedback types equivalent) has value - simplifies deployment to cheapest option

**Robustness Assessment:**
Both efficiency frontier (thesis) and semantic richness (antithesis) are actionable findings for practitioners. Experimental design resolves tension through empirical evidence. Mitigations (R1-R5) address weaknesses from both arguments.

**Confidence:** 0.85 (synthesis integrates both perspectives into falsifiable experimental design)
